# 0004. 작업 설계·구현·검증·검토는 dryforge로 하고, 보조 스킬은 둘만 들인다

- 날짜: 2026-10-06 23시 무렵 · 주체: 팀장

## 맥락

- 지침서의 원래 구현 방식은 오케스트레이터가 서브에이전트에게 지시를 나눠 주고, 독립 검토자 1명을 거쳐 병합하는 수작업 절차였다.
- Hacker 역할 스킬 조사는 데모 경로 디버깅(`systematic-debugging`), 제출 전 검토(`requesting-code-review`), 치명적 로직 최소 시험(`test-driven-development`), 화면 프로토타입(`claude-design`), 구조 그림(`architecture-diagram`)을 추천했다.
- 확인해 보니 앞의 셋은 superpowers 플러그인에 들어 있는데, 이 플러그인은 설치만 돼 있고 꺼져 있었다. 뒤의 둘은 Hermes(다른 에이전트 도구)의 스킬 폴더에만 있었다.

## 결정

- 작업 설계·구현·검증·검토는 dryforge(Claude Code 플러그인, `ready` → `go`)로 한다. 원래 구현 방식(역할, 서브에이전트 지시에 넣을 것, 반환 양식, 검토자에게 줄 것, 트랙 나누기)은 작업 설계 때 참고 자료로 함정·요령 문서에 남긴다.
- superpowers 플러그인은 켜지 않는다. 그 세 스킬이 맡을 일은 dryforge 흐름으로 대신한다.
- `claude-design`, `architecture-diagram`만 이 폴더 `.claude/skills/`(git 추적 제외)에 복사해 쓴다.

## 버린 대안

- **superpowers 플러그인 켜기**: 세 스킬을 바로 쓸 수 있지만, 플러그인이 모든 세션 시작 때 "스킬 먼저 쓰기" 지시를 넣어 당일 작업 순서와 부딪힌다.
- **원래 수작업 운영 유지**: 이미 손에 익은 절차지만, 지시문·검토 요청을 매번 손으로 짜야 한다.

## 결과

- dryforge `go`는 작업 트리가 깨끗해야 시작한다. 기록 파일을 고친 뒤에는 커밋하고 나서 `go`를 부른다. 두 사람의 세션이 같은 폴더를 쓰면 멈출 수 있다.
- `go`가 만드는 브랜치 이름은 `go`의 규칙을 따른다. main 반영은 여전히 squash 병합이다. `go`는 main을 작업 base로 쓰거나(새 프로젝트 판정) 마무리에서 `--no-ff` 병합을 할 수 있어, base가 main이면 멈추고 마무리는 "Hand off only"로 받은 뒤 squash 병합을 따로 한다.
- 복사한 두 스킬은 git이 추적하지 않아 새 clone이나 worktree에는 없다.
