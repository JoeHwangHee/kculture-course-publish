## 2. 팀과 결정권

**팀 구성**은 사람 둘이다. 두 사람 모두 이 저장소에서 에이전트를 쓴다. Hustler는 자기 노트북에서 비공개 GitHub 저장소를 clone해 자기 브랜치로 일하고, 자기 영역(Hacker 경로 밖)의 파일만 만든다. 병합과 main 반영은 팀장 쪽이 한다.
- **사용자: 팀장이자 Hacker(만드는 쪽)**. "시연에서 실제로 작동하는가"를 책임진다.
- **Hustler(검증·설득 쪽)**. "누가 왜 원하는가"를 책임진다. 맡는 일은 실제 문제 경험자 인터뷰, 근거 숫자 조사, 예시 자료·화면 문구, 발표 자료와 대본, 발표다.
- Hacker와 Hustler는 직군 구분이 아니라 **제작 책임**과 **검증·설득 책임**의 구분이다. 디자인은 둘이 나눠 맡는다.

**결정권표**

| 결정 | 정하는 사람 | 에이전트가 하는 일 |
|---|---|---|
| 수요: 누가 왜 원하나, 그 기능이 문제를 푸는가 | Hustler | 기다린다. 대신 정하지 않는다 |
| 접점 1(Hacker와 Hustler가 결과를 맞춰 보는 10분짜리 합류 시점, 12:00)의 방향 유지·전환 | Hustler가 검증 결과로 제안하고 팀장이 정한다 | 구현 가능 범위와 X1 결과를 내놓는다 |
| 미션 해석이 갈릴 때의 선택 | 팀장 | 갈린 해석을 질문 목록으로 올린다 |
| 한 문장 주장, 하는 일 / 하지 않는 일 | 팀장 | 초안을 낸다 |
| 7시간 안에 만들 수 있나, 구현 방식 | 팀장(Hacker) | 선택지와 시간 비용을 낸다 |
| 계약(트랙끼리 함께 기대는 약속)과 그 변경 | 팀장 | 바꿀 일이 생기면 멈추고 올린다 |
| 평가 정의와 그 동결 | 팀장 | 접수 때 승인한 초안대로 동결하면 다시 묻지 않는다. 달라질 때만 묻는다 |
| 미리 정한 줄일 순서 밖의 범위 축소 | 팀장 | 묻는다 |
| 대체 경로와 그 발동 조건 | 팀장(접수 때 승인) | 승인된 단계만 자동 발동하고 바로 알린다 |
| 키, 계정, 라이선스·제3자 고지 수락 | 팀장 | 대신 수락하지 않는다 |
| 공개, 제출, 삭제, 비용, 외부 게시 | 팀장 | 실행 전에 묻는다 |
| 작업 배분, 병합, 수정 1회 뒤 남은 검토 이견(계약이 아닐 때), 조정값 | 팀장의 주 에이전트 세션(오케스트레이터) | 정하고 결정 기록에 한 줄 남긴다 |

- 애매하면 사람이 정할 일로 본다.
- **충돌 해결**: Hustler가 필요하다고 확인한 요구를 팀장이 7시간 안에 구현할 수 없다고 판단하면, **문제는 유지하고 구현 방식을 줄인다**. 예: "노쇼를 예측한다" → "사장님이 예약 확인과 예약금 링크를 보낼 수 있게 한다".
- 기다리는 동안에는 그 결정에 기대는 일만 멈춘다. 기다림을 "승인"이나 "반영 없음"으로 간주하지 않는다.
- 승인된 범위 안에서는 묻지 않고 진행한다. 승인은 미션 접수 끝의 한 번이 기본이다. 그 뒤에는 위 표의 사람 결정이 새로 생길 때만 다시 묻는다 `[DESIGN]`.
- 에이전트 세션은 자기를 띄운 사람과만 말한다. 팀장의 결정이 필요한 일을 Hustler의 세션이 만나면 Hustler를 거쳐 팀장에게 올린다. 서브에이전트(주 세션이 띄운 보조 에이전트)는 사람에게 직접 묻지 않는다.

**Hustler의 수요 검증 기준**(접점 1까지)
1. 해당 문제를 최근 겪은 사람에게 먼저 묻는다. 참가자·멘토 의견은 보조 근거로만 쓴다.
2. 묻는 것: "가장 최근에 언제 있었나", "지금은 어떻게 해결하나", "그 때문에 잃는 시간·돈·기회가 있나".
3. 문제의 빈도, 손실, 지금 대안의 불편함 가운데 둘 이상이 약하면 대상이나 핵심 기능을 줄이거나 바꾼다.
4. 실제 경험자 2명 이상을 목표로 한다. 지인 2명의 의견만으로 시장 수요를 확정하지 않는다.

## 3. 한 문장 주장과 범위

- 주장은 측정할 수 있는 꼴로 쓴다: "A가 B보다 C 조건에서 D 지표가 낫다."
  - 예선 예: "Nemotron이 숫자를 직접 쓴 조사 보고서보다, 검증된 값만 틀에 채우고 검증기로 막는 TradeSentry 보고서가 실제 관세청 자료 경보에서 사실 주장 오류율이 낮다." `[사실: docs/plan/DEV_PLAN.md 59행]`
- 하는 일 / 하지 않는 일은 판단의 성격, 쓰는 사람, 범위로 나누어 쓴다. 과장할 여지를 먼저 막는다. 예선 예: "부정·위법 판정이 아니고, 실제 조치도 아니다."
- **실제로 작동시키는 기능은 하나다.** 시연은 끊기지 않는 장면 하나로 짠다. 그 장면은 "입력 → 핵심 처리(모델·도구 호출) → 사용자에게 보이는 결과"가 실제로 도는 경로이고, 미션이 처음 제시한 문제가 풀리는 순간을 보여야 한다.
  - 목업(시연을 돕는 모형 화면)이어도 되는 것: 주변 메뉴, 설정, 회원가입, 관리자 기능, 장기 분석·예측의 결과 화면.
  - 만들지 않는 것: 마이크로서비스 분리, 인증 체계, 운영 대시보드, 완전한 CI/CD, 확장성 설계.
- 목업은 발표·README에서 실제 동작과 구분해 밝힌다. 목업을 실제 자동화 결과나 검증 결과처럼 보이지 않는다.
- 방향 전환은 접점 1에서 **한 번만** 한다. 기능 동결(접점 2) 뒤에는 새 기능을 넣지 않는다. 안 되는 부분은 고치기보다 시연 동선에서 뺀다.

## 4. 평가

**두 번 동결한다.** 결과는 동결 2 뒤에만 본다.
- **동결 1(구현 전)**: 지표 정의, 사례, 기대 결과, 홀드아웃(개발에 쓰지 않고 마지막에 1회만 돌리는 평가 사례) 분리를 한 커밋으로 고정한다. 접점 1(방향 결정) 뒤에 한다. 접점 1 전에 동결했다가 방향을 바꾸면 평가를 다시 써야 하기 때문이다 `[DESIGN: 사용자 승인 2026-10-06]`.
- **동결 2(측정 전)**: 채점 스크립트를 완성해 커밋한다.
- 동결 커밋 해시는 미션 접수 기록에 적는다.

**지표**
- 결과의 단위는 보고서(결과물) 하나가 기본이다. 주장 단위로 세면 무효 결과가 분모에서 빠지고, 주장끼리 독립이 아니라 구간이 좁게 나온다 `[사실: docs/eval/RULEBOOK.md 487~490행]`.
- 기계가 셀 수 있는 지표를 고른다. 예: 인용한 근거가 원문에 있는지, 막아야 할 요청을 막았는지, 숫자가 원본과 같은지.
- 정답이 한 줄로 정해지지 않는 과제(문서 질의응답, 요약 등)는 정해진 필드와 패턴으로 찾을 수 있는 주장만 채점한다. 의미 정확성은 범위 밖이라고 밝힌다.
- 사례는 5~10개와 기대 결과로 시작한다.
- **기준선**(비교 대상)은 같은 모델·도구·예산·자료를 쓰고 처리 방식만 다르게 둔다. 처음부터 본 시스템과 같이 돌린다. 그래야 차이가 그 처리의 효과가 된다.
- 기준선은 규칙 기반 절차가 못 푸는 과제(정성 판단, 비정형 입력)를 고를 때 의미가 생긴다. 예선은 합성 40건에서 모델 없는 고정 절차 `checklist` 38/40, `agent` 38/40, `full` 35/40으로 구간이 겹쳐 "LLM 추가 가치 미확인"이었다 `[사실: 예선 자기채점]`.

**채점**
- 채점은 결정적(같은 입력이면 같은 결과)이다. 모델이나 AI 채점자를 쓰지 않는다.
- 모든 사실 주장(산문 속 숫자·증감 표현 포함)을 센다. 숫자 칸만 세면 구조상 0%가 나와 당연한 결과로 보인다.

**분모와 재실행**
- 실패, 시간 초과, 무효도 분모에 남긴다. 결과를 본 뒤 어려운 사례를 지우지 않는다.
- 인프라 실패로 다시 돌릴 때는 조건을 채운 실행 **모두**를 1회만 다시 하고, 원래 기록을 남긴다.
- 개발용 사례와 평가용 사례를 시작 때 나눈다. 고치는 데 쓴 사례로 채점하지 않는다.
- 결과를 본 뒤 지표·사례·채점 규칙을 유리하게 고치지 않는다.

## 5. 결과 표기

- 숫자는 채점 스크립트 출력에서만 옮긴다. 손으로 고쳐 쓰지 않는다.
- 비율은 `x/N`과 Wilson 95% 구간(표본이 작을 때 쓰는 비율 신뢰구간)을 함께 쓴다.
  - 계산: `p=x/n`, `d=1+z²/n`, `c=(p+z²/(2n))/d`, `h=z·√(p(1−p)/n + z²/(4n²))/d`, 구간 `[max(0,c−h), min(1,c+h)]`, `z=1.96`.
  - 확인값: 11/40 → 16.1%~42.8%, 0/40 → 0.0%~8.8%, 9/10 → 59.6%~98.2%.
  - 두 구간이 겹치면 차이를 주장하지 않는다. "확인하지 못했다"를 "차이가 없다"로 바꿔 쓰지 않는다.
  - 사례 10건 안팎이면 "참고치"로 표기한다.
- 숫자마다 자료 종류를 붙인다: 개발셋(튜닝에 노출) / 홀드아웃(노출 안 됨) / 합성 / 실자료. 등급은 "누가 정답을 만들었나"와 "정답이 개선 과정에 노출됐나" 두 질문으로만 정한다.
- 대체 경로를 썼으면 어느 단계에서 왜 멈췄는지 적는다. 측정하지 못한 것은 "측정하지 못함"으로 적는다.
- 재생 실행(저장된 모델 응답을 다시 내주는 실행)은 점수 근거가 아니다. 쓰면 "저장된 응답 재생"이라고 밝힌다.
- 시연 실행은 점수 근거와 별개라고 밝힌다.
- 증거 없는 주장은 `[미확인]`으로 두고 병합·보고·발표의 근거로 쓰지 않는다.

**쓰지 않는 서술**(발표와 README를 확정하기 전에 이 목록으로 한 번 검색한다)
- "허용 목록에 있으니 안전하다"
- 합성 숫자를 실자료 숫자처럼 쓰기
- 같은 모델을 두 번 쓴 것을 정확성 보증처럼 쓰기
- 팀 규칙(`[DESIGN]`)을 대회 공식 규칙처럼 인용하기
- 구간 없는 "0%"를 크게 보이기
- 쓰지 않은 기능 언급
- 도메인 판정을 과장하는 말(예선 예: 부정·위법 판정)
- 목업을 실제 동작처럼 보이기

**예선작 소개**: 한 문장 주장과 결과를 말한다. 실자료 40건 보고서 단위 사실 주장 오류율은 기준선 `freeform` 11/40 = 27.5%(16.1%~42.8%), 본 시스템 `full` 0/40 = 0.0%(0.0%~8.8%)이다. 표기 "A등급 주장 보류(참고치)"를 함께 쓴다 `[사실: docs/eval/RESULTS.md]`.

## 6. 대체 경로와 줄일 순서

- NVIDIA 연동마다 타임박스와 대체 경로를 접수 때 적고 팀장 승인을 받는다.
- **승인된 단계만 자동으로 발동한다.** 타임박스를 넘기면 원인과 관계없이 그 경로로 가고 바로 팀장에게 알린다.
- 승인되지 않은 대체 경로는 쓰기 전에 팀장 결정을 받는다.
- 키 주입 방법이 모두 실패했거나 보안 요건을 채우지 못하면 우회하지 않는다. 즉시 팀장 결정을 받는다. 키를 샌드박스 안에 넣는 우회는 하지 않는다.
- 예선 예: 로컬 Docker → Brev 전환은 미리 정한 자동 전환이었다. OpenShell만 쓰는 단계로 내려가는 일과 게이트웨이·키 문제는 사용자가 정했다.
- **줄일 순서 3개와 끝까지 지킬 것 3개**를 접수 때 정한다. 예선 예: "승인 불변식 시험 → 같은 사례 반복 실행 → 화면 3번째 → 화면 2번째" 순서로 줄이고, 대표 지표·비교군·OpenShell 증거는 지켰다. 이 목록 밖의 축소는 팀장 승인을 받는다.

## 7. 자기 점검(심사 기준)

중간 1회, 마무리 1회 한다. 칸은 `기준 | 점수 | 근거 한 줄 | 증거 경로`다.
- 증거가 점수를 정한다. 근거가 비면 무효다.
- 증거가 없으면 찾아본 경로를 적고 낮은 점수를 준다.
- 기준이 두 가지로 읽히면 낮은 쪽으로 해석한다.
- 같은 팀이 채점하면 후해진다는 위험을 적어 둔다.
- 심사 1번(NVIDIA 활용 심도)은 구성요소마다 "빼면 어떤 지표가 나빠지나"로 답한다(삭제 시험). 예선은 NemoClaw, Agent Skills, NAT를 빼도 정확도가 그대로여서 이 점수가 약했다. 본선은 NVIDIA 구성요소가 지표에 직접 닿게 설계한다.
- 예선 최종 자기채점은 73.8/100이었다. 팀 규범 점수이며 공식 배점이 아니다. 예선 팀 채점 규범의 가중치·게이트·점수 기준 문장은 본선에 가져오지 않는다. 규범 스스로 "예선 전용"이라고 적고 있기 때문이다 `[사실: docs/research/SCORING_GOLDEN_RULE.md 269행]`.
